# Site e2e (Playwright)

Unit tests (Vitest + jsdom, `src/**/*.test.*`) cover logic. Playwright (`e2e/`) covers what jsdom cannot:
real audio, real canvas pixels, layout at real sizes, the built output. Use both.

## Run it

```
npm run e2e                                   # build, preview, run everything (desktop 1440x900 + mobile 360x740)
npx playwright test -g "Poké Balls"           # one test by title
npx playwright test --project=mobile          # one viewport
npx playwright show-trace test-results/<dir>/trace.zip   # after a failure
```

- Takes about 50 s (the test that plays the puzzles of the deep cave with motion is the longest, about 16 s). It always runs `npm run build` first and serves `dist/` with `vite preview` on port 4173.
- Browser: on Windows outside CI it drives the Edge that ships with Windows (`channel: 'msedge'`), so no download. Elsewhere, and in CI, it uses Playwright's Chromium (`npx playwright install --with-deps chromium`). Set `PW_CHANNEL=chrome` (or `msedge`) to force an installed browser.
- CI: `.github/workflows/deploy.yml` has an `e2e` job (installs Chromium, runs `npm run e2e`) and the deploy job needs it. The harness runtime gate also runs `npm run e2e` (`.wesharness.json`), so it needs port 4173 free.
- Headless by default (no window opens). Watch it with `npx playwright test --headed --workers=1` or `--ui`.
- Failures leave screenshots and traces in `test-results/` (git-ignored).

## Traps (each one cost time)

1. **Never reuse a running preview server.** An old `vite preview` on 4173 serves a stale `dist/`, and Playwright then skips the rebuild, so tests pass against old code. The config sets `reuseExistingServer: false` for this reason; if the port is busy the run fails loudly. Find and stop the leftover on Windows: `Get-NetTCPConnection -LocalPort 4173 -State Listen` then `Stop-Process -Id <pid> -Force` (`pkill` does nothing here).
2. **Prove a new test can fail.** Break the behaviour on purpose (for example change a volume in the component), run that test, see it fail, then `git checkout` the file. A green test you never saw red proves little. This is how trap 1 was found.
3. **`getByRole` skips hidden elements.** The cat starts hidden (`visibility: hidden` and `inert`), so use `getByRole('button', { name: 'Cat', includeHidden: true })`, or `toBeHidden()`/`toHaveAttribute()` assertions find nothing and time out. The video is found by `getByTitle('Titan cat video')`.
4. **Audio is checked through the real `play()`.** `e2e/helpers.ts` wraps `HTMLMediaElement.prototype.play` before the page loads and records `src`, `volume`, start offset and whether the promise resolved (so autoplay refusals show up). Built asset names are hashed (`cat-AbC123.mp3`), so match a substring, and note `'cat-'` matches the meow but not `cat_rap`. `playsOf(page, 'gb-')` style.
5. **Stub YouTube, and make the stub opaque.** The hidden video is a YouTube embed; `stubYouTube` keeps tests offline. A stub page with a transparent body makes the iframe look empty in screenshots (the rain shows through) even though it is visible. It looked like a bug and was not.
6. **Headless Edge cannot go below about 500 px wide from the CLI** (`msedge --headless --screenshot --window-size=360,...` renders a 500 px layout and crops it). Use Playwright's `viewport`/devices for mobile, never the CLI.
7. **Unfound Poké Balls are almost invisible on purpose.** `pokeball.png` is 2052x2048 and the button shows only its 32x32 corner until found. They are real buttons named `Poké Ball 1`..`4`, so click them by role.
8. **Matrix backdrop.** Click the exposed background at `(3, 3)` to cycle the colour (the glass panel covers the middle). Read pixels with `getImageData` (`litPixels`) to check it rains, stays black under `page.emulateMedia({ reducedMotion: 'reduce' })`, and stops when `document.hidden` is overridden to `true` and `visibilitychange` is dispatched. Storage key: `currentMatrixFontColorIndex`, valid values `0`-`3`; anything else falls back to green. The same index is the site theme: the click also sets `data-theme` (`green|red|blue|white`) and the colour tokens (`--accent`, `--accent-hover`, `--accent-on-light`, `--accent-soft`, `--on-accent`) on `<html>`. Computed colours fade for about 0.4 s, so poll them (`expect.poll`) or emulate `reducedMotion: 'reduce'`, which switches at once. To check there is no flash of the wrong theme, install a `MutationObserver` on `data-theme` in `addInitScript` and assert only the stored theme was ever set (the attribute can be set to the same value more than once, so compare a Set). Palettes and their contrast rules live in `src/features/theme/themes.ts`; colours in CSS cannot be checked by Vitest (`css: false` empties CSS, even `?raw`), so `src/styles/themeTokens.test.ts` reads the files with `node:fs` and the e2e checks the computed result.
9. **The cat overlaps the social bar** (cat z-index 3, bar 2). That is how the original site behaved; it is not a regression.
10. **Panels live in a fixed dialog above the social bar**, not anchored to their button. Check them with `toBeInViewport({ ratio: 1 })` at both viewports; work experience scrolls inside the panel, so the last job starts out of view.

11. **The site routes by hash.** Home is `/` (or `/#/`), projects is `/#/projects`; `openSite(page, '/#/projects')` waits for that page's heading instead of the home h1. The first history entry is the bare address, so after `goBack` expect `/` or `/#/`. On a narrow viewport (`isMobile`) the site menu is a "Menu" button that must be opened before its links exist.
12. **Keep `(3, 3)` clear.** The left menu, the mobile Menu button (at 12px) and the projects page wrapper (`pointer-events: none` around the glass card) must not cover the top-left corner, or the background-click tests fail on the page that covers it.
13. **Home and Projects share one glass geometry.** Same `max-width`, padding (home `.page` mirrors Projects' `.page`) and monospace font from the shared `glass-panel` class in `src/styles/glass.css` (a plain global stylesheet; do not go back to CSS Modules `composes ... from` another module, because it makes `npm run dev` warn that a PostCSS plugin did not pass the `from` option). `body` centres its content vertically and has no padding of its own, and the page padding is symmetric (120px top and bottom), so the glass sits exactly on the window's middle line, level with the fixed, centred site menu; any asymmetry in the page or body padding moves it off that line. They only share a top edge when the Projects page is taller than the window, so the test compares widths and fonts at several widths and the centres against the window and the menu in a 1600px-tall window (do not pin the home page to the top with `margin-bottom: auto`). The Poké Balls sit inside the home glass, spread over empty spots of the whole panel (top, left and bottom padding by px, one beside the text by percentage; the same set from 1300px up, one ball moves into the right padding below that, and a phone set under 700px; a test checks no two are closer than a set distance), and come last in the glass so Tab reaches the name first; the glass is their positioned container and the counter hugs the glass's top edge; both are absolute, so the glass geometry is unchanged.

14. **The terminal page** is `/#/terminal`; `openSite` waits for its h1 "Terminal". The input (`getByRole('textbox', { name: 'Command' })`) is focused on load and again after a click inside the terminal (not on the h1, which sits outside it); output is `getByRole('log', { name: 'Terminal output' })`. The log's text has no whitespace between lines (they are block `div`s), so match `/whoami\s*guest/`, not `\s+`. `theme <name>` and `matrix` change the real site theme, which fades for 0.4 s: poll, or emulate `reducedMotion: 'reduce'`, under which `matrix` prints at once and leaves the colour alone. Rain lines carry `data-kind="rain"` and `aria-hidden`. Tab completes only when the input has text, so on an empty input it moves focus on. Output lines wrap at about 32 characters on a 360px phone, so keep fixed-width art (neofetch) under that.

The Pilot plays a copy of the engine in Node to find the keys; battles are random on the page, so never count presses through one, use `fight()`. Without reduced motion text types itself: press A in a loop until `data-dialogue` is `false`, do not `expect.poll` a press (too few polls fit the timeout). The touch buttons exist only on the mobile project. `tsconfig.e2e.json` includes `vite/client` types because the Pilot imports game modules whose types reach `src/data/projects.ts` (image imports); do not import `projects.ts` itself from e2e, Node cannot load images. 16. **The rain can hold a page up for seconds, so never poll from the test against a short deadline.** On Windows with Edge, one `fillText` of the matrix rain now and then takes 1.1 to 1.8 s (measured by wrapping `CanvasRenderingContext2D.prototype.fillText` in an init script: any character, printable or not, the first call or a later one, in roughly one page load in four to one in two), and under load (16 workers) more than 5 s. The page's main thread stands still meanwhile: timers are late and a `page.evaluate` does not come back. That is what made "finding all four Poké Balls" fail now and then: the fanfare's 2 s timer and the test's `expect.poll(..., { timeout: 5000 })` both sat behind one such call (the trace showed one `Evaluate` of 5.7 s). It is the same on `main` (3 failures in 24 runs of that test with `--workers=16` on c9576c9), so it is not the game: the home page does not mount it. Wait inside the page instead, with the test's own limit: `await played(page, 'victory')` (`e2e/helpers.ts`, a `page.waitForFunction` without a timeout). To hunt a flake: `npx playwright test e2e/site.spec.ts --repeat-each=12 --workers=16 --reporter=line`, then read the times of the calls out of `test-results/<dir>/trace.zip` (`test.trace` holds one JSON line per call with `startTime` and `endTime`). At 16 workers other tests with a 3 or 5 s wait fail the same way now and then (the theme colours, the cat in the viewport, the rain on the projects page); the default (half the cores) is what the suite is kept green on. Since round eleven of the game, `expect` waits 10 s by default (`playwright.config.ts`): with the last fight played with motion (about 45 s) running beside them, the quick checks of the site (an image loaded, the cat video in view, a colour faded in, the rain lit) failed one at a time on a stalled page, a different one on each run. Check a fix for a flake with the whole suite three times over, `npx playwright test --repeat-each=3 --reporter=line`: a test that passes twenty times alone can still fail in the suite, and the other way round.

17. **A key pressed right after `page.emulateMedia` is still played the old way.** The game reads the reduced-motion setting through React, so it follows one render later. A key that lands before that is one whole move with nothing held: holding the arrow then never walks on (the hop test waited 30 s for a cell that never came), and a battle starts without its transition (the frames recorded for it are empty, `Cannot read properties of undefined (reading 'at')`). Use `await setMotion(page, true)` (`e2e/pilot.ts`: it waits for `data-motion`), or `pilot.motion(true)` when the Pilot goes on driving. When measuring how long something lasted from frames recorded in the page, the browser can skip frames right at the end: take the least it lasted up to the first frame after it, and the most over the frames that showed it.

18. **The address changes before the page does.** A click on a link of the site menu changes the hash at once; the router renders the other page a moment later, and the page that leaves tidies up after that (the game closes its AudioContext in an effect cleanup). `await expect(page).toHaveURL(...)` followed by a look at the page's state is therefore a race, and it is lost more often on a quiet machine than on a busy one ("going to another page stops the sound" failed 7 of 8 times in the full suite and never alone). Wait for what the test is about: the other page's heading, the game gone, and the state itself with `page.waitForFunction`.

## Looking at the page (not just asserting)

Assertions do not tell you it looks right. To see it, add a temporary spec such as `e2e/_shots.spec.ts` that opens the site with `openSite(page)`, drives it, and calls `page.screenshot({ path: '<scratchpad>/name.png' })`; run it with `npx playwright test _shots`, `Read` the images, then delete the spec. Do not commit it.

With motion every hit in a battle blinks for about 1.1 s and a press waits for it, so a test that plays battles with motion (the last fight) needs a longer timeout (`test.setTimeout`). B (X) on the title screen switches GB / GBC.

To get a far place on the screen, a temporary `(window as ...).__store = storeRef` (and `__settings = settingsStore`) in `Game.tsx` lets the spec set the state; the canvas only redraws on a change, so press M twice after setting it (it toggles the sound and repaints). Do not press B or X for that: in a battle, a menu or a shop it closes what you wanted to see.

## Adding a test

- Put it in `e2e/*.spec.ts`; start with `const { errors } = await openSite(page)` (it records audio, stubs YouTube and collects console errors) and assert `errors` is empty if the page should be clean.
- Query by role and accessible name like a user; the easter eggs are real buttons with `aria-label`s. State that has no accessible form is exposed as `data-*` (`data-playing`, `data-glasses`, `data-visible`, `data-found`).
- Run it on both projects. Keep timeouts honest: the cat rap is the slow clip.
- Logic that does not need a browser belongs in Vitest instead (`src/**/*.test.*`; Vitest is configured to ignore `e2e/`).

## Unit-test learnings (Vitest)

- `userEvent` under `vi.useFakeTimers()` hangs. Use `vi.useFakeTimers({ shouldAdvanceTime: true })`, and assert timer boundaries with margins (1800 ms absent, 2200 ms present), not exact milliseconds, because real time leaks in.
- jsdom has no media playback or canvas: `src/test/setup.ts` stubs `play`/`pause`, `src/test/fakeAudio.ts` records `Audio` instances, and canvas tests mock `getContext`.

## Other repo facts

- Checks: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `npm run e2e` (the harness runtime gate runs all five; CI runs them too).
